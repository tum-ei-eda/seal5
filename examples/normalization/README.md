# LLVM 23 normalization example

`examples/demo.py` includes this example and its configuration when
`LLVM_REF=llvmorg-23.*`. Only the
`Normalization` model enables the optional memory, register, subscript, and
branch passes. It also opts in to experimental memory and recognized branch
patterns through `check_pattern_support.allow_memory` and `allow_branches`.
Other models retain the default pattern exclusions. Multi-output operations
and gisel-table patterns are not enabled.
The example raises `behav_to_pat.added_complexity` to prefer its generated
rules over equivalent native rules during selection tests.

The example covers:

- RV32 dynamic scalar slices in both directions, with inclusive widths.
- RV32 little-endian halfword/XLEN loads and halfword stores.
- RV64 XLEN loads and automatic low-word register names.
- RV32/RV64 loads and stores with register offsets and scaled register offsets.
- Fused arithmetic on load/store data and on both the address and data.
- AND/OR/XOR-nonzero and single-register nonzero branch conditions.
- Manually written `MEM8`, `MEM32`, and `XW` accesses.
- A conditional PC-relative branch with the RISC-V B-format displacement.
- Register-versus-immediate branch conditions: unsigned 3-bit and signed 5-/8-bit
  immediates, including an RV64 signed comparison. Condition operand names and
  widths are independent of the signed 13-bit destination operand.
- GlobalISel instruction selection and assembler/disassembler round trips.

The extra checker also runs automatically after the LLVM 23 demo tests. It
verifies the normalized split CDSL, generated memory and branch patterns, and
invokes the built pattern-gen on the memory instructions. It checks LLVM load/store widths and
writes a JSON report to `.seal5/temp/normalization_checks/results.json`.
The lit tests check actual GlobalISel selection for loads, a truncating store,
indexed and fused memory operations, and conditional branches, in addition to
object emission/disassembly. The memory fixtures use ordinary pointers and GEPs;
shared volatile loads and intervening aliasing stores check the limits of load folding.
XOR-nonzero is tested through its equivalent register-inequality IR form.
Postincrement/writeback and read-modify-write operations remain excluded.
The branch-immediate tests cover negative and positive bounds, out-of-range
fallback/rejection, immediate operand ordering, and object emission/disassembly.
Type inference preserves explicit signed casts so negative condition immediates
are not accidentally reinterpreted as unsigned values.
`pattern_gen_compare_immediates_llvm23.patch` canonicalizes condition immediates
to the right side of comparisons, swapping the predicate when necessary. This
lets ordinary GlobalISel patterns match either source operand order.

The example applies a small LLVM 23 pattern-gen patch for dynamic slices.
The original aligned-access shortcut rounded variable offsets down to element
boundaries. The patch limits that shortcut to proven aligned constants; the
code-generation test includes an unaligned three-bit offset.

It also applies `pattern_gen_codegen_llvm23.patch`, containing the RISC-V
backend support from CoreDSL2LLVM commits `6b2cb1e9d` and `4c01dcdfb`:
branch intrinsic legalization, B-format operands and branch handling, and
narrow-store selection. The optional standalone include/build switches are
omitted because Seal5 installs generated instructions itself.
The separate `pattern_gen_narrow_store_llvm23.patch` handles explicit low-bit
register slices used as store values, which otherwise reach PatternGen as
narrow register loads and abort during pattern printing.

`pattern_gen_memory_fusion_llvm23.patch` exposes pointer arithmetic before
selecting its memory users, retaining pointer-typed copies for native fallback.
Generated memory patterns ignore those copies while retaining GlobalISel's
safe-fold checks; nested loads additionally require a single use to prevent
duplicating memory accesses. Autogenerated load tests return their register result
so a competing store-data pattern cannot absorb it. Store address registers are treated as inputs by Seal5's
operand analysis.
